# Feedback log

Running log of gaps we hit in Serverpod 4, the `serverpod_offline_sync` module, Serverpod Cloud and their docs while building Chorus. It becomes the hackathon's "Most Valuable Feedback" form.

Pins this log is written against: Serverpod 4.0.4, `serverpod_offline_sync_server` / `serverpod_offline_sync_client` 0.0.10, Flutter 3.47.7.

## How to use this log

- Add a row the moment something costs us time. Do not wait for a fix.
- **Status** has two values:
  - `observed in docs, not yet reproduced`: read in the docs, README, source or pricing page; we have not run code that shows it.
  - `reproduced`: we ran it. Add the date, the spike or test that shows it, and the exact error text or behaviour.
- Never move a row to `reproduced` from memory. If a spike shows the docs were right and we were wrong, strike the row through and say so; do not delete it.
- Before filing: drop every row still marked "not yet reproduced" unless the form makes clear it is a docs observation, and attach a link (file and tag, or page URL) to each remaining row.

| # | Date | Area | What we hit | Why it matters | Suggested fix | Status |
|---|---|---|---|---|---|---|
| F01 | 2026-10-13 | Offline sync: versions | The module README on `main` documents 0.0.11, which needs a Serverpod 4.1 beta. There is no compatibility table for people on stable Serverpod. | A stable 4.0.x user who follows the README, or runs `pub add` without a version, gets a release that does not match their Serverpod. The working docs are only at the `0.0.10` tag, which nothing points to. | A compatibility table at the top of the README (module version, Serverpod version, link to the docs at that tag), and a note on pub.dev. | observed in docs, not yet reproduced |
| F02 | 2026-10-13 | Offline sync: platforms | No statement of Android or iOS support, and the example app has no `android` folder. | Offline sync matters most on phones. Without a statement, a team cannot tell whether mobile is supported, untested or known broken before committing to it. | A platform support table (Android, iOS, web, macOS, Windows, Linux: supported / untested / not supported) and an Android target in the example app. | observed in docs, not yet reproduced |
| F03 | 2026-10-13 | Offline sync: client API | No sync-status or connectivity API, and no auto-reconnect. | Every app must write its own supervisor (restart on connectivity change and on resume, backoff) and its own status indicator, and cannot honestly show "up to date" without guessing. | A status stream on the client (connecting, live, backoff, last merge time, unsent changes) and built-in reconnect with backoff, or a documented recipe. | observed in docs, not yet reproduced |
| F04 | 2026-10-13 | Offline sync: conflicts | The loser of a unique-index conflict can be detected only by string-matching a `__conflict__` suffix in the column value. | The conflict is the most interesting thing the engine does, and apps can reach it only by parsing an undocumented string format that could change between versions. | A typed flag on the row or a typed conflict event (table, column, winner id, loser id), and a documented, stable suffix format in the meantime. | observed in docs, not yet reproduced |
| F05 | 2026-10-13 | Offline sync: server | The server is not notified when a client's changes merge. | Server-side reactions to synced data (live views, notifications, derived rows) need a second channel: a streaming endpoint or a syncing client. | A server-side hook or stream fired after a merge commits, carrying the space, the user and the changed tables. | observed in docs, not yet reproduced |
| F06 | 2026-10-13 | Offline sync: docs | The README's server snippet, which calls `session.db.transactionForUser`, does not compile. | It is the first thing a reader copies for server-side writes into synced tables. A broken snippet leaves no documented way to do it. | Fix the snippet and compile the README's code in CI. Show the accessor that works, and how to exercise it in the generated test tools. | observed in docs, not yet reproduced |
| F07 | 2026-10-13 | Offline sync: spaces | Reads span every space the user belongs to, and `spaceId` comes back null on rows. | An app with more than one shared space cannot tell which space a row belongs to, so it has to add and maintain its own column (ours is `circleId`) on every synced table. | Return `spaceId` on read, and allow a query to be scoped to one space. | observed in docs, not yet reproduced |
| F08 | 2026-10-13 | Offline sync: access | Read-only members read everything in the space, and revoking a member leaves the rows already on their device. | Apps holding personal data must tell users plainly that removal does not recall data. There is no narrower read scope to offer. | Document both behaviours prominently. Consider wiping a space's rows from the local replica when access is revoked, or an event the app can act on. | observed in docs, not yet reproduced |
| F09 | 2026-10-13 | Offline sync: client API | No hook to defer applying a merge. | Some screens must not change under the user (in our case, a child mid-sentence on a picture board). The app has to render from its own held snapshot and reconcile by hand. | An option to pause and resume applying incoming changes, or a pending-changes stream the app applies when it chooses. | observed in docs, not yet reproduced |
| F10 | 2026-10-13 | Offline sync: web setup | `sqlite3.wasm` and `db_worker.js` for web are a manual step, and the files must match the versions in `pubspec.lock`. | Without the first file the database cannot open in a browser. Getting the versions right is manual and easy to get wrong after any dependency change. | A CLI command or build step that fetches the matching files, or a check at start-up that names the expected version. | observed in docs, not yet reproduced |
| F11 | 2026-10-13 | Serverpod Cloud: plans | The Starter plan disables future calls. This is shown on the pricing page but not in the docs. | An app that relies on scheduled jobs deploys cleanly on Starter and then its jobs never run. A reader of the future-calls docs is not warned. | A note in the future-calls docs and the Cloud deploy docs, and a warning from `serverpod cloud` when the project registers future calls on a plan without them. | observed in docs, not yet reproduced |
| F12 | 2026-10-13 | Offline sync: examples | No worked example of a shared space with several users. The example app shows only a personal space. | Shared spaces are the reason to choose the module for collaborative apps. The pattern has to be pieced together from `docs/shared-spaces.md` and the module's tests. | An example with two or three users in one shared space, including a read-only member and a unique-index conflict. | observed in docs, not yet reproduced |

| F13 | 2026-10-13 | Database: testing | `serverpod_database` 4.0.4 keeps one process-wide `ValueEncoder`, replaced whenever a `Database` is constructed. A Postgres server and a SQLite replica in one isolate render each other's dialect. | The module's own test pattern (server and client replicas in one test process) fails unchanged: `operator does not exist: uuid = bit` on the server and `UNIQUE constraint failed: offline_sync_spaces.uuidSpaceId` on the replica. Our workaround imports two `serverpod_database/src` files. | Make the encoder a property of the database or session, not a global. | reproduced 2026-10-13, spike S4; workaround in `chorus_server/test/sync/replicas.dart` |
| F14 | 2026-10-13 | Offline sync: testing | The generated test tools (`withServerpod`) build a server without the sync engine. | `session.offlineSync` throws `StateError` in every endpoint test of an app that uses shared spaces, until the test passes `databaseInterceptor: offlineSyncDatabaseInterceptor` and calls `initializeOfflineSync(syncTables: ...)` itself. | Have the generator wire the module into the test tools when `databaseSync` is on. | reproduced 2026-10-13, spike S4; `chorus_server/test/integration/circle_endpoint_test.dart` |
| F15 | 2026-10-13 | Offline sync: access | A member made read-only on the server while holding an unsynced write gets no error from `syncOnce`. The server never takes the row; it stays on the author's device looking saved. | An app cannot tell its user that an edit was refused. | Report refused changes to the client: an exception, or a callback naming the rows. | reproduced 2026-10-13, spike S4 scenario "T8 stale" in `chorus_server/test/sync/spaces_test.dart` |
| F16 | 2026-10-13 | Offline sync: client API | A write outside `transactionForUser` for a row of a shared board is hidden at once, even from its author: no error, the unique key becomes `<value>__hidden__<id>` and ordinary reads omit it. | The most likely mistake with shared spaces produces a row that silently vanishes. | Throw, or log a warning in debug mode, when a write lands in the personal space but references a row in a shared one. | reproduced 2026-10-13, spike S4 scenario T9 in `chorus_server/test/sync/spaces_test.dart` |
| F17 | 2026-10-13 | Offline sync: client API | `syncOnce` cannot be cancelled and, unlike the continuous mode, has no timeout of its own (`engine.dart`: once-mode reads the inbound stream without the idle timeout). | An app that gives up on a slow one-shot sync cannot stop it, must not start another on the same session while it may still be merging, and cannot safely close the database under it. | A cancellable handle for `syncOnce`, as `syncContinuously` already returns, and an optional timeout. | observed in docs, not yet reproduced (read in source at 0.0.10) |
| F18 | 2026-10-13 | Database: exceptions | Inserting a row whose primary key already exists in the SQLite replica throws the base `DatabaseQueryException` (`UNIQUE constraint failed: board.id`, code 1555), not `DatabaseUniqueViolationException`, which a unique-index clash (code 2067) does throw. | Code that catches the unique-violation type to make an insert idempotent misses the primary-key case. | Map SQLite 1555 to `DatabaseUniqueViolationException` too. | reproduced 2026-10-13, spike S4 scenario "T7 retry" in `chorus_server/test/sync/merge_test.dart` |
| F19 | 2026-10-13 | Web server: routing | The scaffold's `server.dart` puts a `FallbackMiddleware` on `/` (directly, and inside `FlutterRoute`) that replaces every 404 with the web app's start page. A custom route cannot answer 404: the browser gets the Flutter app with status 200. | A link that has expired or never existed shows the app's sign-in page instead of "not found". We return 410 for it. | Let a route mark its response as final, or apply the fallback only to paths no route matched. Say so in the web-server docs. | reproduced 2026-10-13 by the engineer who built the print route; `chorus_server/test/integration/print_test.dart`, "when the web server is asked for /print/<token> then the route answers ..." asserts the 410 over HTTP. Not re-run by hand against a started server. |
| F20 | 2026-10-13 | Testing: generated tools | `withServerpod` does not start the web server and does not set up the auth services. | A test of a web route has to start the web server itself; a test that signs a user in has to call `initializeAuthServices` itself, and because `emailIdp.login` opens its own transaction it also needs `RollbackDatabase.disabled`. | Options on `withServerpod` to start the web server and to initialise auth as `server.dart` does. | reproduced 2026-10-13; `chorus_server/test/integration/print_test.dart` and `demo_seed_test.dart` |
| F21 | 2026-10-13 | Cloud storage: uploads | `verifyDirectFileUpload` on the database storage only checks that the file exists. Size is bounded by the ticket; content is not checked at all. | An app that names files by their hash must fetch the bytes back and re-hash them on the server to know the client sent what it said. | An optional checksum on the upload description that the storage verifies, as object stores do. | reproduced 2026-10-13; `chorus_server/test/integration/media_endpoint_test.dart`, "when the uploaded bytes do not match the hash then the file is refused and removed ..." |
| F22 | 2026-10-13 | Cloud storage: uploads | The database storage keeps one live upload key per path, and with `preventOverwrite` a second upload to a path that already has bytes is refused with 403 or 409. `FileUploader.uploadByteData` reports all of that as `false`. | Two people uploading the same content-addressed file, or one retry, look like a failed upload although the bytes are there. The client must call its own "confirm" endpoint after a `false` to find out. | Return a result that tells "already there" from "failed", or document the status codes. | observed in docs, not yet reproduced (read in source at 4.0.4 by the engineer who built the media endpoints; no test drives a real HTTP upload) |
| F23 | 2026-10-13 | Cloud storage: uploads | The upload endpoint `/serverpod_cloud_storage` ignores `maxRequestSize` and uses the ticket's `maxFileSize` instead. | Good behaviour, but undocumented: we nearly raised `maxRequestSize` for the whole API to allow a 600 KB clip. | One sentence in the upload docs. | observed in docs, not yet reproduced (read in `public_endpoint.dart` at 4.0.4) |
| F24 | 2026-10-13 | Client: addresses | The generated client knows the API server's address only. A native app has no way to learn where the project's web server is. | Any feature that hands a person a web link (a printable page, a share page) needs its own endpoint that returns `session.serverpod.config.webServer`'s public address, or a build-time define. | Expose the web server's public address to the client, as `assets/config.json` already does for the API address on the web. | reproduced 2026-10-13; we added `printing.pageUrl`, tested in `print_test.dart` "when the app asks where a page is ...".
